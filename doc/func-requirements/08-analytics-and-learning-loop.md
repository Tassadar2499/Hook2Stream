# 08. Аналитика и learning loop

Документ определяет функциональные требования к продуктовым событиям, учёту переменной стоимости, статусам и метрикам публикаций, отчётам кампании и персонализированным рекомендациям.

Product KPI и целевые пороги из базового плана являются критериями оценки продукта, а не гарантированным результатом отдельной кампании. Система должна рассчитывать их из фактических событий, но не должна представлять прогноз как доказанный performance.

## Product и cost telemetry

### FR-MET-001 — Регистрация продуктовых событий

**Этап:** P0 / Core MVP  
**Актор:** Система; Администратор  
**Источник:** [§ 6.8 «Аналитика и learning loop»](../base/AI_Content_Factory_SaaS_Plan.md#68-аналитика-и-learning-loop), [§ 12.2 «Основные KPI»](../base/AI_Content_Factory_SaaS_Plan.md#122-основные-kpi)  
**Требование:** Система должна регистрировать ключевые события пользовательского пути release campaign.

**Правила и предусловия:**

- как минимум фиксируются `qualified_signup`, `upload_started`, `upload_completed`, `candidates_ready`, `candidate_selected`, `candidate_rejected`, `render_started`, `render_completed`, `project_completed` и `export_completed`;
- событие содержит тип, timestamp, workspace, project и идентификатор объекта действия, когда он применим;
- событие не должно связываться с чужим workspace;
- повторная доставка одного логического события не должна удваивать агрегаты.

**Критерии приёмки:**

- **AC-01**
  - **Дано:** пользователь успешно начал и завершил загрузку исходника;
  - **Когда:** система сохраняет lifecycle загрузки;
  - **Тогда:** аналитика содержит по одному связанному событию `upload_started` и `upload_completed` с теми же workspace и project.
- **AC-02**
  - **Дано:** одно событие `render_completed` доставлено обработчику повторно;
  - **Когда:** система обновляет аналитические агрегаты;
  - **Тогда:** завершённый render учитывается один раз.

**Связанные FR:** FR-MET-002, FR-MET-003, FR-MET-004, FR-BIL-001

### FR-MET-002 — Учёт времени редактирования и feedback кандидатов

**Этап:** P0 / Core MVP  
**Актор:** Пользователь; система  
**Источник:** [§ 6.5 «Candidate Review и Clip Editor»](../base/AI_Content_Factory_SaaS_Plan.md#65-candidate-review-и-clip-editor), [§ 6.8 «Аналитика и learning loop»](../base/AI_Content_Factory_SaaS_Plan.md#68-аналитика-и-learning-loop)  
**Требование:** Система должна сохранять выбор `Select`/`Reject` и фактическое активное время редактирования клипа как аналитический feedback.

**Правила и предусловия:**

- feedback связывается с конкретным candidate, analysis run и project;
- повторное изменение выбора сохраняет актуальное состояние и историю событий без двойного подсчёта одного действия;
- edit time не должен включать время, когда редактор закрыт или неактивен;
- feedback P0 используется для аналитики, а персонализированное ранжирование включается только в P2.

**Критерии приёмки:**

- **AC-01**
  - **Дано:** пользователь отклонил предложенный candidate;
  - **Когда:** действие успешно сохранено;
  - **Тогда:** система регистрирует rejection, связанный с этим candidate и analysis run.
- **AC-02**
  - **Дано:** пользователь редактировал клип, затем закрыл редактор;
  - **Когда:** сессия редактирования завершается;
  - **Тогда:** система сохраняет активное edit time и не продолжает увеличивать его после закрытия редактора.

**Связанные FR:** FR-MET-001, FR-MET-003, FR-MET-009

### FR-MET-003 — Расчёт продуктовой воронки

**Этап:** P0 / Core MVP  
**Актор:** Администратор  
**Источник:** [§ 12.2 «Основные KPI»](../base/AI_Content_Factory_SaaS_Plan.md#122-основные-kpi)  
**Требование:** Система должна рассчитывать продуктовую воронку и временные метрики из зарегистрированных фактических событий.

**Правила и предусловия:**

- поддерживаются этапы signup/upload, upload/candidates ready, candidate/edit, completed project/export;
- time-to-value рассчитывается между завершённой загрузкой и готовностью previews;
- candidate acceptance рассчитывается по фактическим `Select` и `Reject`;
- целевые пороги из продуктового плана показываются отдельно от фактических значений и не подменяют их.

**Критерии приёмки:**

- **AC-01**
  - **Дано:** проект имеет `upload_completed` в T1 и `candidates_ready` в T2;
  - **Когда:** система рассчитывает time-to-value;
  - **Тогда:** значение равно интервалу между T1 и T2 для этого проекта.
- **AC-02**
  - **Дано:** в когорте есть завершённые и незавершённые пользовательские пути;
  - **Когда:** администратор просматривает конверсию `completed project → export`;
  - **Тогда:** система использует фактические числитель и знаменатель когорты, а не целевой KPI.

**Связанные FR:** FR-MET-001, FR-MET-002, FR-MET-004

### FR-MET-004 — Определение Successful Release Campaign

**Этап:** P0 / Core MVP; расширяется в P1  
**Актор:** Система; Администратор  
**Источник:** [§ 12.1 «North Star»](../base/AI_Content_Factory_SaaS_Plan.md#121-north-star)  
**Требование:** Система должна считать release campaign успешной, если в течение 14 дней пользователь выбрал (`Selected`) и экспортировал либо подтвердил публикацию не менее шести уникальных роликов проекта.

**Правила и предусловия:**

- в P0 учитываются clean exports кандидатов, имеющих пользовательское состояние `Selected`;
- в P1 дополнительно учитываются публикации только в состоянии `Published`;
- `AwaitingUserAction`, `Processing`, `Failed` и простая генерация candidate не засчитываются;
- один и тот же clip export/publication не должен удваивать число уникальных роликов кампании.

**Критерии приёмки:**

- **AC-01**
  - **Дано:** за 14 дней пользователь перевёл в `Selected` и экспортировал шесть разных роликов проекта;
  - **Когда:** система рассчитывает North Star;
  - **Тогда:** кампания помечается Successful Release Campaign.
- **AC-02**
  - **Дано:** проект имеет пять подтверждённых exports и одну TikTok-запись `AwaitingUserAction`;
  - **Когда:** система рассчитывает North Star;
  - **Тогда:** кампания не считается успешной из-за отсутствия шестого подтверждённого результата.

**Связанные FR:** FR-MET-001, FR-PUB-004, FR-PUB-009

### FR-MET-005 — Cost telemetry проекта

**Этап:** P0 / Core MVP  
**Актор:** Система; Администратор  
**Источник:** [§ 6.8 «Аналитика и learning loop»](../base/AI_Content_Factory_SaaS_Plan.md#68-аналитика-и-learning-loop), [§ 11.1 «Единица продукта»](../base/AI_Content_Factory_SaaS_Plan.md#111-единица-продукта)  
**Требование:** Система должна учитывать фактические единицы переменного потребления по каждому проекту.

**Правила и предусловия:**

- учитываются source seconds, analysed seconds, rendered output seconds, storage byte-days, AI calls/tokens, publication attempts, retries и delivery;
- данные связываются с workspace, project, job и provider operation, когда это применимо;
- неуспешная попытка учитывает фактически понесённые затраты, но не подменяет entitlement transaction;
- стоимость должна быть доступна для admin cost breakdown.

**Критерии приёмки:**

- **AC-01**
  - **Дано:** analysis и два final render завершились успешно;
  - **Когда:** система формирует cost telemetry проекта;
  - **Тогда:** запись содержит проанализированные секунды и сумму rendered output seconds обеих версий.
- **AC-02**
  - **Дано:** render завершился ошибкой после частичной обработки и затем был повторён;
  - **Когда:** администратор открывает breakdown;
  - **Тогда:** система показывает фактические затраты обеих попыток отдельно от пользовательского списания entitlement.

**Связанные FR:** FR-MET-001, FR-BIL-001, FR-BIL-003, FR-ADM-004

## Публикации и platform performance

### FR-MET-006 — Сохранение идентичности публикации

**Этап:** P1 / V1  
**Актор:** Система; пользователь с правом публикации  
**Источник:** [§ 6.8 «Аналитика и learning loop»](../base/AI_Content_Factory_SaaS_Plan.md#68-аналитика-и-learning-loop)  
**Требование:** Система должна сохранять platform post ID, URL, состояние обработки и время последней синхронизации публикации.

**Правила и предусловия:**

- сохраняются только значения, фактически полученные от официального API или подтверждённого workflow;
- отсутствие post ID или URL не заменяется вымышленным значением;
- идентификаторы связываются с конкретной publication и `ClipVersion`;
- доступ к записи ограничен её workspace.

**Критерии приёмки:**

- **AC-01**
  - **Дано:** площадка вернула post ID и URL для подтверждённой публикации;
  - **Когда:** система синхронизирует результат;
  - **Тогда:** значения сохраняются вместе с publication, `ClipVersion` и timestamp синхронизации.
- **AC-02**
  - **Дано:** TikTok Upload находится в `AwaitingUserAction` и post ID ещё отсутствует;
  - **Когда:** система показывает публикацию;
  - **Тогда:** она не создаёт фиктивный post ID или URL и не показывает запись как `Published`.

**Связанные FR:** FR-PUB-003, FR-PUB-004, FR-PUB-009, FR-MET-007

### FR-MET-007 — Синхронизация официальных performance-метрик

**Этап:** P1 / V1  
**Актор:** Пользователь; система  
**Источник:** [§ 6.8 «Аналитика и learning loop»](../base/AI_Content_Factory_SaaS_Plan.md#68-аналитика-и-learning-loop)  
**Требование:** Система должна получать performance-метрики публикации только из официально доступных API выбранной площадки.

**Правила и предусловия:**

- базовый набор может включать views, likes, comments и доступные watch metrics;
- расширенные outcome metrics относятся к P2 и определены отдельно в `FR-MET-012`;
- частота синхронизации задаётся `CFG-METRICS-SYNC-INTERVAL` после закрытия `DEC-013`;
- недоступная метрика показывается как unavailable, а не как ноль;
- Instagram-метрики не включаются до закрытия `DEC-008`.

**Критерии приёмки:**

- **AC-01**
  - **Дано:** официальный API вернул views и likes, но не вернул watch metrics;
  - **Когда:** система сохраняет snapshot;
  - **Тогда:** views и likes содержат фактические значения, а watch metrics отмечены недоступными.
- **AC-02**
  - **Дано:** Instagram verification gate `DEC-008` не закрыт;
  - **Когда:** пользователь открывает доступные источники performance;
  - **Тогда:** система не обещает и не генерирует неподтверждённые Instagram-метрики.

**Связанные FR:** FR-PUB-017, FR-MET-006, FR-MET-008, FR-MET-010, FR-MET-012

### FR-MET-008 — История metric snapshots

**Этап:** P1 / V1  
**Актор:** Система; пользователь  
**Источник:** [§ 9.2 «Основные доменные сущности»](../base/AI_Content_Factory_SaaS_Plan.md#92-основные-доменные-сущности), [§ 6.8 «Аналитика и learning loop»](../base/AI_Content_Factory_SaaS_Plan.md#68-аналитика-и-learning-loop)  
**Требование:** Система должна сохранять timestamped `MetricsSnapshot` без двойного учёта повторно полученного состояния.

**Правила и предусловия:**

- snapshot связывается с publication, platform post ID и временем получения;
- повторный идентичный ответ не увеличивает накопительные метрики;
- более новый snapshot не переписывает историческое значение предыдущего;
- retention snapshots задаётся `CFG-METRICS-RETENTION` после закрытия `DEC-013`.

**Критерии приёмки:**

- **AC-01**
  - **Дано:** для публикации получены snapshots в T1 и T2;
  - **Когда:** пользователь просматривает историю;
  - **Тогда:** система сохраняет оба состояния с их timestamp и показывает актуальным T2.
- **AC-02**
  - **Дано:** один и тот же ответ площадки обработан повторно;
  - **Когда:** система пересчитывает метрики кампании;
  - **Тогда:** накопительные значения не удваиваются.

**Связанные FR:** FR-MET-006, FR-MET-007, FR-MET-010

## Learning loop V2

### FR-MET-009 — Учёт предпочтений артиста в ранжировании

**Этап:** P2 / V2  
**Актор:** Пользователь; система анализа  
**Источник:** [§ 6.4 «Музыкальный и визуальный анализ»](../base/AI_Content_Factory_SaaS_Plan.md#64-музыкальный-и-визуальный-анализ), [§ 6.8 «Аналитика и learning loop»](../base/AI_Content_Factory_SaaS_Plan.md#68-аналитика-и-learning-loop)  
**Требование:** Система должна учитывать прошлые `Select`/`Reject` и подтверждённый performance артиста при ранжировании кандидатов следующей кампании.

**Правила и предусловия:**

- используются только данные того же артиста или разрешённого workspace-контекста;
- пользовательский manual candidate и ручное решение остаются доступны;
- рекомендация объясняет, какой прошлый тип section, opening hook, duration, subtitle preset или CTA повлиял на неё;
- использование и retention learning data регулируются `CFG-METRICS-LEARNING-CONSENT` и `CFG-METRICS-RETENTION` после закрытия `DEC-013`;
- система не обещает вирусность или гарантированный performance.

**Критерии приёмки:**

- **AC-01**
  - **Дано:** у артиста есть разрешённая история feedback и performance;
  - **Когда:** система ранжирует кандидаты нового проекта этого артиста;
  - **Тогда:** она учитывает историю и показывает причину персонализированной рекомендации.
- **AC-02**
  - **Дано:** использование learning data для workspace запрещено активной политикой;
  - **Когда:** система формирует новый набор кандидатов;
  - **Тогда:** она не использует сохранённый персональный performance, но сохраняет базовый scorer и ручной override.

**Связанные FR:** FR-MET-002, FR-MET-007, FR-MET-011

### FR-MET-010 — Сравнение клипов по признакам кампании

**Этап:** P2 / V2  
**Актор:** Пользователь  
**Источник:** [§ 6.8 «Аналитика и learning loop»](../base/AI_Content_Factory_SaaS_Plan.md#68-аналитика-и-learning-loop), [§ 12.3 «Outcome-метрики V2»](../base/AI_Content_Factory_SaaS_Plan.md#123-outcome-метрики-v2)  
**Требование:** Система должна сравнивать подтверждённый performance клипов по section, opening hook, duration, subtitle preset, CTA и platform.

**Правила и предусловия:**

- сравнение использует фактические snapshots и атрибуты опубликованной `ClipVersion`;
- сравниваются только доступные и сопоставимые метрики;
- отсутствие данных обозначается явно;
- корреляция не представляется как доказанная причинность.

**Критерии приёмки:**

- **AC-01**
  - **Дано:** несколько опубликованных клипов имеют section, duration и platform metrics;
  - **Когда:** пользователь группирует отчёт по section;
  - **Тогда:** система показывает фактические агрегаты для каждой доступной группы.
- **AC-02**
  - **Дано:** у одной группы отсутствует watch metric;
  - **Когда:** пользователь сравнивает completion rate;
  - **Тогда:** система помечает группу как несопоставимую, а не подставляет ноль.

**Связанные FR:** FR-MET-007, FR-MET-008, FR-MET-011

### FR-MET-011 — Отчёт release campaign

**Этап:** P2 / V2  
**Актор:** Пользователь  
**Источник:** [§ 6.8 «Аналитика и learning loop»](../base/AI_Content_Factory_SaaS_Plan.md#68-аналитика-и-learning-loop)  
**Требование:** Система должна формировать отчёт по результатам конкретного релиза и артиста.

**Правила и предусловия:**

- отчёт связывает candidates, выбранные версии, exports, publications и доступный performance;
- отчёт отделяет фактические публикации от exports и `AwaitingUserAction`;
- общий счётчик сгенерированных клипов не считается достаточным результатом кампании;
- данные другого артиста или workspace не включаются без разрешения.

**Критерии приёмки:**

- **AC-01**
  - **Дано:** релиз содержит exports, опубликованные клипы и доступные metric snapshots;
  - **Когда:** пользователь открывает campaign report;
  - **Тогда:** система показывает результаты по этому релизу с разделением exports и подтверждённых publications.
- **AC-02**
  - **Дано:** проект создал десять candidates, но ни один не был экспортирован или опубликован;
  - **Когда:** пользователь открывает отчёт;
  - **Тогда:** система не представляет десять generated candidates как успешный outcome кампании.

**Связанные FR:** FR-MET-004, FR-MET-006, FR-MET-008, FR-MET-009, FR-MET-010

### FR-MET-012 — Расширенные outcome metrics

**Этап:** P2 / V2  
**Актор:** Пользователь; Система  
**Источник:** [§ 12.3 «Outcome-метрики V2»](../base/AI_Content_Factory_SaaS_Plan.md#123-outcome-метрики-v2)

**Требование:** Система должна синхронизировать и показывать расширенные outcome metrics только тогда, когда они официально доступны для конкретной платформы и connection scope.

**Правила и предусловия:**

- Расширенный набор может включать 3-second hold, average percentage viewed, completion rate, saves/shares, smart-link transitions и subscriptions after view.
- Каждая metric хранит platform definition, окно и timestamp snapshot; метрики с разной семантикой не объединяются как одинаковые.
- Недоступное значение показывается как unavailable, а не как ноль или оценка.
- Sync, retention и consent регулируются `DEC-013`.

**Критерии приёмки:**

- **AC-01:** **Дано** официальный API возвращает completion rate и saves, **когда** система синхронизирует publication, **тогда** она сохраняет фактические значения с platform definition и snapshot timestamp.
- **AC-02:** **Дано** площадка не предоставляет subscriptions after view, **когда** пользователь открывает advanced report, **тогда** система показывает metric как unavailable и не рассчитывает вымышленное значение.

**Связанные FR:** FR-MET-006, FR-MET-007, FR-MET-008, FR-MET-010, FR-MET-013

### FR-MET-013 — Сравнение A/B hook variants

**Этап:** P2 / V2  
**Актор:** Пользователь  
**Источник:** [§ 10.4 «V2»](../base/AI_Content_Factory_SaaS_Plan.md#104-v2-ещё-1420-недель), [§ 12.3 «Outcome-метрики V2»](../base/AI_Content_Factory_SaaS_Plan.md#123-outcome-метрики-v2)

**Требование:** Система должна позволять объединить две или более immutable `ClipVersion` в A/B hook experiment и сравнить их фактический performance по заранее выбранным сопоставимым метрикам.

**Правила и предусловия:**

- Каждая variant сохраняет собственный opening hook, publication и metric snapshots.
- Правила assignment, сравнимые platform/time windows, attribution и minimum data определяются `DEC-018`.
- Отчёт показывает ограничения сравнения и не представляет наблюдаемую разницу как доказанную причинность.
- Изменение hook создаёт новую `ClipVersion`, а не переписывает variant.

**Критерии приёмки:**

- **AC-01:** **Дано** две опубликованные hook variants входят в один experiment и имеют сопоставимые snapshots, **когда** пользователь открывает сравнение, **тогда** система показывает выбранные метрики по каждой variant и применённые attribution/window rules.
- **AC-02:** **Дано** variants опубликованы в несопоставимых условиях по `DEC-018` либо данных недостаточно, **когда** пользователь запрашивает вывод, **тогда** система помечает сравнение ограниченным и не объявляет победителя как доказанный результат.
